# Reset and Clock Semantics

> Normative reference for how clocks, resets, and the surrounding sequential machinery interact with RHIF semantics. RHIF kernels are pure functions; sequential semantics (registers, flip-flops, post-reset behaviour) live one level up, in the `Synchronous` and `Circuit` traits. This document is the boundary contract.

## RHIF is pure

A kernel function (an `Object`) is a pure function over `Digital` values. There is no notion of "clock edge" or "register update" *inside* an opcode. Each call to `execute(obj, args)` is a single combinational evaluation: the inputs go in, the outputs come out, no state crosses calls.

In particular:

- There is no opcode that "delays by one clock cycle."
- There is no opcode that observes time.
- There is no implicit shared state between sequential calls of the same kernel.
- A kernel can be called any number of times with any inputs and produces consistent results.

Sequential behaviour comes from *outside* — from the framework's `dff::DFF`, `Constant`, FIFO, and similar sub-circuits, which the `Synchronous`/`Circuit` traits arrange around a kernel.

## The `Synchronous` model

A typical kernel has signature:

```rust
fn kernel(cr: ClockReset, i: I, q: Q) -> (O, D)
```

Where:

- `cr: ClockReset` — the implicit clock + reset, distributed by the framework.
- `i: I` — combinational inputs.
- `q: Q` — the *current* value of every sub-circuit (a tuple/struct of values, one per `dff::DFF`).
- `o: O` — combinational outputs.
- `d: D` — the *next* value of every sub-circuit (mirroring `q`'s shape).

In each clock cycle, the framework:

1. Samples the inputs `i` and the current state `q` (where `q` reflects the previous cycle's `d`).
2. Calls `kernel(cr, i, q)` to produce `(o, d)`.
3. Latches `d` into the sub-circuit DFFs on the active clock edge.

Reset is handled by the surrounding sub-circuits: each `dff::DFF<T>` has an internal "post-reset value" of `T::default()`; when `cr.reset` is asserted, the DFF stays at the default value regardless of `d`.

The kernel itself sees `cr` as an opaque value. The convention `cr.reset.any()` is what kernels use to "branch on whether reset is asserted" (see [Reset semantics](#reset-semantics-in-the-kernel)).

## `ClockReset` and its inner kinds

`ClockReset` is a `Digital` struct with two fields:

```rust
pub struct ClockReset {
    pub clock: Clock,
    pub reset: Reset,
}
```

`Clock` and `Reset` are nominal one-bit kinds. They are *not* produced by any kernel opcode — they enter the kernel via the `cr` argument and are consumed by:

- `Index(_, cr.reset, [Field("any")])` (or its desugar) to extract the reset condition as a `Bits(1)`.
- (Rarely) reading `cr.clock` directly, though this is unusual; clock semantics are imposed externally.

The framework guarantees that `cr.reset` is asserted for at least the configured number of post-power-up cycles, then drops to inactive. The kernel sees this behaviour through the `cr.reset` field.

## Reset semantics in the kernel

The convention enshrined in CLAUDE.md is:

> **Reset comes last.** Compute everything as if reset were not asserted, then unconditionally overwrite with reset values inside the `if cr.reset.any()` block.

In RHIF terms, the kernel body looks roughly like:

```
... opcodes that compute `d.*` and `o.*` in normal-operation mode ...

# If reset is asserted, overwrite:
cr_reset_field <- Index(cr, [Field("reset")])
reset_any      <- Index(cr_reset_field, [Field("any")])    -- a Bits(1)

# For each output field:
o.x_normal     <- ... (the just-computed value)
o.x_reset      <- ... (the reset-time value, typically a literal or a default)
o.x            <- Select(cond=reset_any, true=o.x_reset, false=o.x_normal)

# Same for d.* fields.
```

In source the user writes:

```rust
let mut o = Out::dont_care();
let mut d = D::dont_care();
... compute o, d normally ...
if cr.reset.any() {
    o = Out::default();
    d = D::default();
}
(o, d)
```

The desugar produces `Splice` opcodes for each field of `o` and `d`, all gated by `Select` opcodes on `reset_any`. The kernel does *not* explicitly model "the next cycle's value is `d` if not reset, default if reset" — that contract is delegated to the surrounding `dff::DFF` sub-circuit.

## Sub-circuit composition

A `Synchronous` widget composes sub-circuits — typically `dff::DFF<T>` instances. The kernel reads the *current* value of each sub-circuit via `q.<field>` and writes the *next* value via `d.<field>`. The `Q` and `D` structs are auto-generated by the `SynchronousDQ` derive and have one field per sub-circuit.

At lowering time, each `dff::DFF<T>` becomes a Verilog flip-flop whose:

- `D` input is `d.<field>` from the kernel.
- `Q` output is `q.<field>` to the kernel.
- Clock is the framework-distributed `clk`.
- Reset is the framework-distributed `rst` (active-high in RHDL convention), which forces `Q = T::default()`.

The kernel runs once per clock cycle (in the simulator: per `clock_pos_edge` event; in synthesis: combinationally between flip-flop edges). The kernel itself is unaware of clock cycles — it just produces `(o, d)` from `(cr, i, q)`.

## Clock domains and `Color`

A multi-clock-domain widget uses the `Circuit` trait (asynchronous) and may have multiple clock signals. RHDL's clock-domain safety is *type-system*-enforced: every sub-value tagged with `Color::Red` is incompatible with one tagged `Color::Blue`. The kernel cannot mix them; only an explicit `Retime` (which represents an explicit synchroniser) can change a value's `Color`.

See [`opcodes/retime.md`](./opcodes/retime.md) and [`type-system.md`](./type-system.md#the-signaltc-discipline) for the type-system rules.

The framework synthesises the actual clock distribution: a `Signal<T, Red>` value is wired to the `Red` clock domain in the resulting RTL; cross-domain data flow happens only through `Retime`-annotated synchronisers.

## Reset distribution

The framework supports both synchronous and asynchronous resets at the framework level (configurable per board-support package). At the RHIF level, `cr.reset.any()` is the kernel's view: a single 1-bit signal indicating "any reset is asserted." How the reset is actually implemented (synchronous, asynchronous, multi-cycle deassertion handshake) is a framework concern, not an RHIF concern.

## Relationship between RHIF and the iterator simulator

The iterator-based simulator in `crates/rhdl-core/src/sim/` runs widgets cycle-by-cycle:

- Generate input stream.
- Apply `with_reset(N)` to prepend reset cycles.
- Apply `clock_pos_edge(period)` to convert to a clocked stream.
- For each clock edge: read inputs, read current `q`, call `kernel(cr, i, q)` (which is the RHIF VM call), latch `d` for the next cycle.

The RHIF VM is what's invoked inside this loop. It runs once per cycle on the (cr, i, q) tuple. The simulator's notion of "time" is external; RHIF still has no temporal concepts.

## Summary

| Concept | Lives in |
|---|---|
| Combinational logic | RHIF (this spec) |
| Flip-flops | `dff::DFF` sub-circuit, lowered to Verilog FFs |
| Clock distribution | `Synchronous`/`Circuit` traits, lowered by framework |
| Reset distribution | `Synchronous`/`Circuit` traits |
| Reset value | `T::default()` per sub-circuit |
| Cycle-by-cycle iteration | iterator simulator (`sim`); not in RHIF |
| Cross-domain synchronisation | `Retime` opcode (kernel-level type tag) + an external synchroniser |

A pass author touching RHIF should never need to think about clocks. A widget author touching `Synchronous` builds on the sequential model. The boundary is the kernel signature `fn kernel(cr, i, q) -> (o, d)`, and on the kernel side of that boundary, RHIF is purely combinational.
