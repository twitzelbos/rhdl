# RHDL deep dive

A working understanding of Samit Basu's RHDL based on reading `~/projects/rhdl` at commit `c99d5cc5` (Feb 2026). This document covers four angles: an end-to-end walk of one widget through the IR stack, a catalog of the public API surface, a map of where AI assistance plugs in, and a comparison to the closest peer HDLs.

---

## 1 — End-to-end: the FIFO write-logic kernel

The synchronous FIFO at `crates/rhdl-fpga/src/fifo/synchronous.rs` is built from three sub-circuits — `FIFOWriteCore`, `FIFOReadCore`, and an `OptionSyncBRAM`. The top-level `fifo_kernel` is a pure wiring kernel; the actual logic lives in `write_logic` and `read_logic`. We'll trace `write_logic` because it's small enough to reason about every stage and exercises most of the interesting transformations.

### Stage 0: the Rust source

```rust
#[derive(Clone, Debug, Synchronous, SynchronousDQ, Default)]
#[rhdl(dq_no_prefix)]
pub struct FIFOWriteCore<const N: usize>
where rhdl::bits::W<N>: BitWidth,
{
    write_address:         dff::DFF<Bits<N>>,
    write_address_delayed: dff::DFF<Bits<N>>,
    overflow:              dff::DFF<bool>,
}

#[derive(PartialEq, Debug, Digital, Clone, Copy)]
pub struct In<const N: usize> { pub read_address: Bits<N>, pub write_enable: bool }

#[derive(PartialEq, Debug, Digital, Clone, Copy)]
pub struct Out<const N: usize> {
    pub full: bool, pub almost_full: bool, pub overflow: bool,
    pub ram_write_address: Bits<N>, pub write_address: Bits<N>,
}

impl<const N: usize> SynchronousIO for FIFOWriteCore<N> {
    type I = In<N>; type O = Out<N>; type Kernel = write_logic<N>;
}

#[kernel]
pub fn write_logic<const N: usize>(cr: ClockReset, i: In<N>, q: Q<N>) -> (Out<N>, D<N>) {
    let full        = (q.write_address + 1) == i.read_address;
    let almost_full = full || (q.write_address + 2) == i.read_address;
    let overflow    = q.overflow || (i.write_enable && full);
    let will_write  = !full && i.write_enable;
    let write_address = q.write_address + if will_write { 1 } else { 0 };
    let mut d = D::<N>::dont_care();
    d.write_address_delayed = q.write_address;
    d.write_address         = write_address;
    d.overflow              = overflow;
    let mut o = Out::<N>::dont_care();
    o.full = full;  o.almost_full = almost_full;
    o.write_address     = q.write_address_delayed;
    o.ram_write_address = q.write_address;
    o.overflow          = overflow;
    if cr.reset.any() {
        d.write_address = bits(0);  d.overflow = false;
        o.full = false; o.almost_full = false;
        o.write_address = bits(0); o.ram_write_address = bits(0); o.overflow = false;
    }
    (o, d)
}
```

A few things to notice already. The kernel is plain Rust — `if`-as-expression, `mut` locals reassigned at the bottom, struct field updates, `==`, `+`, `&&`, `||`. The `Q<N>` and `D<N>` types are auto-generated by `#[derive(SynchronousDQ)]` from the struct fields: `Q.write_address` has the type of `DFF::O = Bits<N>`, and so on. The clock and reset (`cr: ClockReset`) are not explicitly fanned to the children — that happens automatically because we're inside a `Synchronous` circuit.

### Stage 1a: AST capture by the `#[kernel]` macro

`rhdl-macro-core/src/kernel.rs` walks the `syn` AST of the function and serializes it as RHDL's own AST type (`rhdl_core::ast::ast_impl::KernelFn`). It validates against the supported subset (no references, no `&mut`, no closures, no heap, no unsupported expressions), and stores the resulting AST as a `const` so the compiler can pick it up later via the `DigitalFn` trait: `K::kernel_fn() -> Some(KernelFnKind::AstKernel(...))`.

### Stage 1b: MIR + type inference

`compile_design_stage1<K>` (in `compiler/driver.rs`) pulls the AST, runs `compile_mir` to lower it to a typed MIR (`compiler/mir/mir_impl.rs`), then `infer` (`compiler/mir/infer.rs`) — type inference uses the `ena` crate for union-find on type variables. This is where generic params like `N` get monomorphized and where Rust's `==`, `+`, `||` get resolved to bit-vector or boolean operations. Path types (struct/tuple/enum field accesses, like `q.write_address`) are interned for compactness.

### Stage 1c: RHIF (typed SSA)

After type inference, MIR lowers to RHIF — defined in `rhif/spec.rs`. RHIF is a strongly-typed SSA virtual-machine instruction set. Every value is a `Slot`; each instruction has a specific opcode. For `let full = (q.write_address + 1) == i.read_address`, RHIF would look approximately like:

```
r1 = Index(arg_q, .write_address)        // q.write_address
r2 = AsBits(literal 1, kind=Bits<N>)     // typed 1
r3 = Binary(Add, r1, r2)                 // q.write_address + 1
r4 = Index(arg_i, .read_address)
r5 = Binary(Eq, r3, r4)                  // bool
// `full` symbol is bound to r5
```

The `if cr.reset.any() { ... }` block becomes a `Select` cascade: each variable assigned inside the if becomes a phi-node-style mux between the reset value and the non-reset value. RHIF keeps the type of each slot explicit, so a downstream pass can always answer "is this a `Bits<N>` or a `bool`."

Stage-1 RHIF passes (run as a fixed-point loop until the IR stops changing) include: `CheckClockDomain` (rejects mixing different `Color`s without explicit retiming), `TypeCheckPass`, `DataFlowCheckPass` (catches use-before-write), `PartialInitializationCheck` (`dont_care()` then partial assignment is allowed; partial reads are not), `ConstantPropagation`, `DeadCodeElimination`, `RemoveUnneededMuxes`, `LowerInferredCasts`, `LowerInferredRetimes`, `PrecomputeDiscriminants` (for enum match), `RemoveExtraRegisters`, `PropagateLiterals`. Each pass is a function `Object -> Result<Object>`; after each pass `SymbolTableIsComplete` re-runs as a sanity invariant.

The CheckClockDomain pass is the one that actually enforces the phantom-color clock-domain marker. It walks the dataflow graph and refuses to combine signals carrying different colors except across an explicit `Retime` op (the `OpCode::Retime` variant in `rhif/spec.rs`).

### Stage 2: RTL (untyped SSA, bit-level)

`compile_design_stage2` lowers RHIF to RTL (`compiler/lower_rhif_to_rtl.rs` + `rtl/spec.rs`). RTL drops the rich type information — every operand is just an `Operand` with a bit-width. Aggregate types collapse: a `Bits<N>` and a `bool` and a struct field access all become bit-range operations. The opcode set shrinks to `Assign, Binary, Case, Cast, Concat, Index, Select, Splice, Unary` — note `Index` here is a bit-range index (`r2 = r1[3:0]`), not a path access.

Stage-2 passes refine and shrink: `LowerSignalCasts`, `RemoveExtraRegisters`, `LowerMultiplyToShift` (mul by power-of-two), `LowerShiftByConstant`, `LowerShiftsByZeroToCopy`, `LowerNotEqualZeroToAny`, `LowerEmptySpliceToCopy`, `LowerIndexAllToCopy`, `LowerSingleConcatToCopy`, `StripEmptyArgsFromConcat`, `RemoveEmptyFunctionArguments`, `RemoveUnusedOperandsPass`, plus the same `ConstantPropagationPass` and `DeadCodeEliminationPass`. The compiler iterates these to a fixed point, hashing the IR each pass to detect when no change happened.

### Stage 3: NTL (netlist) and optimization

`optimize_ntl` (`compiler/stage3.rs`) lowers RTL to NTL (`ntl/spec.rs`), a true netlist where each value is one or more `Wire`s. Opcodes: `Assign, Binary, Vector` (vectorized bitwise op across wires), `Case, Select, Not, BlackBox, Unary`. A 4-bit add becomes a `Vector(Add, [w0..w3], [w4..w7], [w8..w11], signed=false)`. Each output wire is either driven once or by a `Select`/`Case`.

Stage-3 passes: `CheckForUndriven` (wires with no driver — a hard error that maps directly to a Rust source-line diagnostic), `RemoveExtraLiteralsPass`, `ConstantRegisterElimination`, `LowerCase`, `LowerSelects`, `RemoveExtraRegistersPass`, `ConstantPropagationPass`, `LowerBitwiseOpWithConstant`, `LowerAnyAll`, `DeadCodeElimination`, `SingleRegisterWrite` (each register has exactly one driver). When the NTL hash stops changing, it's done.

### Stage 4: Verilog emission

NTL emits Verilog through the `rhdl-vlog` AST (`crates/rhdl-vlog`). This is the "no more string templating" win — the emitter constructs a typed `ModuleDef` of `Declaration`s, `Stmt`s, and `Expr`s, then prints it via the `Pretty` formatter. From the test in `crates/rhdl/tests/tutorial_xor.rs`, you can see the actual emitted form for a tiny kernel: a top-level `module` with a `function` containing one register per slot, an unrolled assignment per RHIF op, and a final assignment to the function's return register. The xor case looks like:

```verilog
module xor_gate(input wire [1:0] i, output wire [0:0] o);
   wire [0:0] od;
   assign o  = od[0:0];
   assign od = kernel_xor_gate(i);
   function [0:0] kernel_xor_gate(input reg [1:0] arg_0);
         reg [1:0] r0; reg [0:0] r1; reg [0:0] r2; reg [0:0] r3;
         begin
            r0 = arg_0;
            r1 = r0[0:0];
            r2 = r0[1:1];
            r3 = r1 ^ r2;
            kernel_xor_gate = r3;
         end
   endfunction
endmodule
```

For a synchronous circuit like `FIFOWriteCore`, the emission also generates the always-block for the DFFs, the reset wiring, and an instance hierarchy rather than a flat function. The `iverilog` integration in `rhdl-toolchains` then runs the emitted Verilog under a real Verilog simulator and compares its waveform against the Rust simulator's waveform — that's what the `tm.run_iverilog()` calls in the test files do.

### Verification handle

The framework gives you four parallel ways to evaluate the same kernel:

1. Pure Rust unit tests on the kernel function (the `test_full_condition`, `test_reset_condition` tests in `write_logic.rs` — call `write_logic(cr, i, q)` directly, assert on `(o, d)`).
2. Rust-side iterator simulation through the `Synchronous` trait (`uut.run(stream)`), with `with_reset`, `clock_pos_edge`, etc.
3. Flow-graph simulation at NTL level via `tb.ntl(&uut, &Default::default())?` — exercises the lowered netlist.
4. Verilog ground-truth via `tm.run_iverilog()` — exercises the emitted Verilog through `iverilog`.

Each level catches a different class of bug: (1) catches algorithmic, (2) catches sequencing, (3) catches lowering, (4) catches Verilog-emission. The fact that all four can be expressed as `cargo test` harnesses is the major ergonomic difference from any traditional HDL flow.

## 2 — Public API surface (what users actually touch)

Sourced from `crates/rhdl/src/prelude.rs`. Grouped by what role they play.

**Bit-vector data types** (`rhdl_bits`).
- `Bits<N>`, `SignedBits<N>` — fixed-width 2's-complement integers, all ops wrap.
- Aliases `b1..b128`, `s1..s128` — saves typing.
- Constructors: `bits(...)`, `signed(...)`, `BitWidth` trait, `W<N>` type-level marker.
- Extension traits for widening ops: `XAdd`, `XSub`, `XMul`, `XNeg`, `XSgn` — produce a result one bit wider so you don't lose carry.
- `BitX` — single 4-state bit (0/1/X/Z).

**Type-system primitives** (`rhdl_core::types`).
- `Digital` — every synthesizable type implements this. Covers `bool`, `Bits/SignedBits`, fixed arrays, tuples, structs, enums (including data-carrying), `Option`. Auto-derivable.
- `Timed` — types that carry a clock domain. Auto-derivable.
- `Signal<T, Domain>` — `T: Digital` lifted into a clock domain. `signal(value)` constructs one; `.val()` reads.
- `Domain` trait + colors `Red, Orange, Yellow, Green, Blue, Indigo, Violet`. Author your own colors trivially.
- `Clock`, `Reset`, `ResetN`, `ClockReset`, `clock(b)`, `reset(b)`, `reset_n(b)`, `clock_reset(c, r)`.
- `TimedSample`, `timed_sample` — for testbench input streams.
- `Kind` (runtime structural type), `Path` (field/variant access), `path!(...)` macro, `bit_range`, `sub_trace_type`.
- `TraceKey`, `trace`, `trace_push_path`, `trace_pop_path` — annotation hooks for tracing.

**Circuit traits** (`rhdl_core::circuit`).
- `Circuit` (combinational/asynchronous), `CircuitIO`, `CircuitDQ` — the async family.
- `Synchronous`, `SynchronousIO`, `SynchronousDQ` — the synchronous family with implicit ClockReset.
- `Func`, `Adapter` — wrapping a kernel directly as a circuit, or adapting between async and sync.
- `Descriptor`, `HDLDescriptor`, `AsyncKind`, `SyncKind`, `ScopedName` — runtime reflection of the design.
- `Fixture`, `Driver`, `MountPoint`, `passthrough_input_driver`, `passthrough_output_driver`, `bind!` macro — top-level test/synthesis fixtures, including the `bind!(fixture, name -> input.path)` ergonomics that wire ports to nested struct paths.
- `drc` — design-rule checks.

**Macros** (`rhdl_macro`).
- `#[kernel]` — the synthesizable function annotation.
- `#[derive(Digital)]`, `#[derive(Timed)]`, `#[derive(Circuit)]`, `#[derive(CircuitDQ)]`, `#[derive(Synchronous)]`, `#[derive(SynchronousDQ)]`.
- `#[rhdl(...)]` attribute knobs (e.g. `dq_no_prefix`, custom discriminant alignment).
- `path!(a.b.c)` — type-safe path literal.
- `export!` — exposes a Rust kernel for use from non-Rust callers.
- `bind!` — port wiring for fixtures.

**Compiler driver** (`rhdl_core::compiler`, `rhdl_core::rtl`, `rhdl_core::ntl`).
- `compile_design::<K>()` — the one-shot Rust→RTL pipeline.
- `compile_design_stage1::<K>()` — Rust→RHIF only, useful for tooling.
- `CompilationMode` — verbose/quiet, debug/release-style.
- `rtl::vm::execute` — run an RTL `Object` directly (the flow-graph simulator).
- `ntl::builder::{constant, circuit_black_box, synchronous_black_box}` — wrap external IP as opaque NTL nodes.
- `RHDLError` — a `miette`-decorated error type carrying source spans.

**Simulation harness** (`rhdl_core::sim`).
- Iterator combinators: `clock_pos_edge`, `with_reset`, `without_reset`, `uniform`, `merge_map`.
- Run extensions: `RunExt` (async), `RunSynchronousExt` (sync), `RunSynchronousFeedbackExt` (closed-loop testing where the next input depends on the current output), `run_async_red_blue` (two clock domains).
- Probes: `ProbeExt`, `SynchronousProbeExt`, `AroundEventExt`, `synchronous_sample` — extract clean per-cycle samples from a continuous-time waveform.
- Testbenches: `TestBench`, `SynchronousTestBench`, `TestBenchOptions`, `tb.rtl(uut, opts)`, `tb.ntl(uut, opts)`, `.run_iverilog()`.

**Tracing & visualization** (`rhdl_core::trace`).
- `Session`, `TracedSample`, `traced_at_time`.
- `VcdFile`, `VcdOptions`, `dump_to_file` — VCD waveform output.
- `SvgFile`, `SvgOptions`, `to_string` — embeddable SVG waveform output (used in the mdbook docs).
- `rhdl-surfer-plugin` (separate WASM crate) — Surfer waveform-viewer plugin that understands enriched RHDL trace types (sees the original enum variants and struct fields, not just bit ranges).

**Verilog AST** (`rhdl_vlog`, re-exported as `vlog`).
- `Pretty` formatter, `parse_quote_miette!` macro, full AST for `ModuleDef`, `Declaration`, `Stmt`, `Expr`. You don't normally touch this — it's used by the codegen — but it's available if you want to template Verilog yourself.

**Widget library** (`rhdl-fpga`, separate crate).
- `core::{counter, dff, delay, option, slice, ram, constant}`.
- `cdc::{synchronizer, cross_counter}` — clock-domain crossing primitives.
- `gray` — gray-code converters for async-FIFO pointer crossing.
- `fifo::{synchronous, asynchronous}` — both with `In<T>`/`Out<T>` interfaces.
- `stream` — backpressure stream cores: `map, filter, filter_map, flatten, zip, tee, chunked, stream_buffer, fifo_to_stream, stream_to_fifo, pipe_wrapper`. Modeled on AXI Ready/Valid handshake.
- `axi4lite::{manager, endpoint, switch, register, channel, bridge}`.
- `dsp::lerp`, `rng::lazy_rng`, `pipe`, `tristate`, `lid`, `reset` (reset conditioners, negation).
- `doc::write_svg_as_markdown` — used to embed waveforms in widget rustdoc.

**Board-support packages** (`rhdl-bsp`).
- Drivers for Lattice and Xilinx primitives (`ibufds`, `open_collector`).
- Full XEM7010 (OpalKelly) board with sys-clock and LED drivers, MIG memory interface project files.
- Constraint emission to `.xdc` (Xilinx) format.

If you're building an AI prompt context: the tightest "minimum viable" surface is `Digital`, `Timed`, `Signal`, `Clock`/`Reset`/`ClockReset`, `Synchronous` + `SynchronousIO` + `SynchronousDQ`, `#[kernel]`, the `Bits`/`bool` primitives, and the `dont_care()` + field-mutation idiom. That's enough to produce any combinational or sequential design. Everything else (sim, trace, vlog, widget library, BSP) is layered on top.

## 3 — AI-assist intervention map

Where Claude (or any LLM agent) plugs in productively, ranked by leverage and feedback quality.

### Tier 1 — high leverage, fast feedback loop

**Kernel synthesis from natural-language spec.** The kernel is the unit of synthesizable code, and it's a pure `fn` over `Digital` types. Because the type system is so strict, an LLM that emits a kernel either compiles (overwhelmingly likely correct shape) or fails with a `miette`-decorated error pointing at the source span. Loop is: prompt → emit `#[kernel] fn` → `cargo check` → if failing, feed compiler diagnostics back. Then `cargo test` the kernel against unit assertions. Eval harness: a corpus of (NL spec, reference kernel, test suite) triples; metric is pass rate at N retries. The widget library doc/ folder is essentially this corpus already — every widget has a doc string describing its function.

**Widget porting from RustHDL.** README plan items are open: "Port the `RustHDL` widget library to `RHDL`" and "Port the various FPGA BSPs to `RHDL` from `RustHDL`." The old RustHDL widgets are public on GitHub and have well-defined behavior. This is structured translation with strong ground truth — give the LLM the RustHDL source, the RHDL Synchronous trait conventions (DQ structure, ClockReset, kernel signature), and one or two examples; let it produce candidate ports. Verification is automatic: simulate both side-by-side under the same input stream, diff outputs. Eval harness writes itself.

**Property and testbench generation.** Given a `#[kernel]` with named struct inputs/outputs, generate `proptest`-style property tests. Examples: "for any `In<N>` with `write_enable == false`, `d.write_address == q.write_address`." The ADT/struct layout makes property generation tractable; the iterator-based simulation makes property checking a one-liner. This pairs naturally with the existing `expect_test`-style golden files for VCDs.

### Tier 2 — high leverage, slower feedback

**Compiler-pass authoring.** The pass infrastructure (`rhif_passes/`, `rtl_passes/`, `ntl_passes/`) follows a uniform pattern: each pass implements `trait Pass { fn run(Object) -> Result<Object> }` and is composed in a fixed-point loop. New optimizations (e.g. bit-width-narrowing, common-subexpression elimination at RHIF level, retiming, register-balancing) can be added in isolation. An LLM with access to existing passes as exemplars can write new ones. Verification is the existing pass test machinery — most passes already ship with `expect_test` snapshots of before/after IR.

**Diagnostics improvement.** README notes "Revisit precise diagnostics & debug/release builds." All errors carry source spans through `rhdl-span` and surface via `miette`. An LLM can audit error sites for clarity and add structured suggestions (e.g. "consider using `Retime` here to cross from `Red` to `Blue`"). High-impact for users; verifiable by user-study or by example-based snapshots.

**Timing-aware refactoring.** RHDL has a longest-path heuristic estimator that traces back to source code (figure 1 of the LATTE '25 paper). Given a slow critical path, an LLM can propose refactorings (insert a register here, split this comparator, move this computation to the previous cycle). Feedback loop: rerun timing estimator, diff. The closed-loop "3rd-party tool feedback into source" RHDL aspires to is precisely an LLM-amenable task.

### Tier 3 — research-grade, valuable but harder to evaluate

**End-to-end FPGA flow orchestration.** Rust kernel → Verilog → place-and-route (yosys/nextpnr or Vivado) → bitstream → board. An LLM agent driving the whole flow, interpreting P&R reports, choosing constraint files, debugging timing closure. The BSP infrastructure already emits XDC; the iverilog hook already exists; what's missing is yosys/vivado integration and the agent harness itself.

**Surfer-plugin-driven debugging.** The `rhdl-surfer-plugin` exposes RHDL-aware traces in the Surfer waveform viewer — enums show as variant names, structs as fields, not raw bits. An agent can read a waveform, identify the cycle and signal of a failing assertion, and propose a kernel fix. This is the equivalent of LLM-driven `gdb`.

**Spec-to-architecture decomposition.** Given a high-level spec ("a 4-channel AXI-Stream demux with backpressure"), produce a decomposition into widget-library components plus the gluing kernel. The fact that `rhdl-fpga::stream` is composable like Rust iterators makes this look very much like ordinary Rust agentic code generation.

### Eval harness sketch

A repeatable evaluation for any of the above: a `tasks/` directory of `task_<name>/` folders, each containing a `spec.md`, a `reference.rs` kernel, and a `test.rs`. The harness invokes the LLM with the spec, the standard prelude context, and a few exemplar widgets. It runs `cargo test --package <task>`, captures pass/fail and any `miette` diagnostics, optionally retries with diagnostics fed back, and records pass-rate / iterations / token-cost.

Because every kernel is also a normal Rust function, you get this harness "for free" from `cargo test`. No simulator integration, no Verilog harness needed for the inner loop. That's the under-appreciated AI-assist superpower of RHDL relative to traditional HDLs.

## 4 — Comparison vs Chisel, Spade, SpinalHDL

A targeted comparison on the dimensions that matter for AI-driven design tooling.

### Language embedding

- **RHDL.** Plain Rust. The kernel is a real `fn`; type-checking happens in `rustc` first, RHDL's compiler runs after. Generics and `const` generics work; trait bounds work; `cargo test` works without a wrapper.
- **Chisel.** Embedded DSL in Scala. The user's "code" is Scala that builds a circuit graph at runtime; the graph is then lowered through FIRRTL. Strong ecosystem (used in industry: SiFive, RocketChip, the open-source RISC-V world), but Scala is the largest barrier to adoption.
- **SpinalHDL.** Also a Scala-embedded DSL, similar architecture. More builder-pattern, fewer macros than Chisel. Strong industrial use.
- **Spade.** A standalone language with Rust-inspired syntax compiled by its own compiler. Not embedded — you write `.spade` files, run `swim` to build. Lighter weight than Chisel; smaller community.

For LLMs: training data favors Chisel/SpinalHDL (more public Scala HDL exists than Rust HDL) but Rust as a language is exceptionally well-represented. Spade has the least training data. RHDL benefits from Rust's general training corpus while needing the LLM to learn just the specific subset.

### IR layering

- **RHDL.** RHIF (typed SSA) → RTL (untyped SSA) → NTL (netlist) → Verilog AST → Verilog. Three IRs plus AST. Each is exposed and pass-extensible.
- **Chisel.** Chisel data structures → FIRRTL (the durable IR) → optimized FIRRTL → Verilog. FIRRTL is the lingua franca; CIRCT is now the LLVM-style umbrella.
- **SpinalHDL.** Direct lowering to Verilog/VHDL through internal IR; less of a separate exposed IR.
- **Spade.** Spade source → MIR → Verilog. Two IRs.

RHDL's three-tier IR is comparable in ambition to FIRRTL/CIRCT's, with the difference that everything is in one Cargo workspace and all in Rust. CIRCT has wider industry buy-in but vastly more setup cost.

### Type system & safety

- **RHDL.** Phantom-color clock domains enforced by `rustc`. ADTs (data-carrying enums) first-class. Bit widths in `const` generics. "If it compiles, the timing-domain story is correct" is a strong invariant.
- **Chisel.** Good types for hardware (UInt, SInt, Vec, Bundle), no native ADTs in the Rust sense (data-carrying enums require workarounds), clock domain handled via `withClock(clk) { ... }` blocks at the API level rather than the type level. Recent Chisel 6 has stronger type ergonomics.
- **SpinalHDL.** Similar story to Chisel; strong typed Bundles, clock domains as runtime objects.
- **Spade.** Strong types, sum types (enum-like), pipelined types. Less mature than the others.

RHDL has the strongest static guarantees of the four, by virtue of using Rust's type system directly. That's the single largest differentiator for AI-driven workflows: the LLM gets a fast, precise, terminal "this is wrong" signal.

### Verification ergonomics

- **RHDL.** `cargo test`. Direct kernel calls, iterator-based simulation, golden VCD/SVG, `iverilog` round-trip — all via standard Rust testing infrastructure.
- **Chisel.** ChiselTest / ChiselSim. Decent but distinct from `sbt test`. Verilator integration is the gold standard.
- **SpinalHDL.** SpinalSim with Verilator backend; very fast but a separate API surface.
- **Spade.** Built-in simulator and testbench DSL; less mature ecosystem.

RHDL's "kernel is just a Rust fn you can call" is the cleanest. Chisel/SpinalHDL with Verilator are faster for huge designs but require more setup.

### Ecosystem & widget libraries

- **Chisel.** Largest by far. RocketChip, BOOM, Constellation, Diplomacy, the entire CHIPS Alliance stack. Industrial deployments.
- **SpinalHDL.** Solid library: VexRiscv, NaxRiscv, AXI/AHB/Wishbone IPs.
- **RHDL.** `rhdl-fpga` is functional but small. README explicitly lists "port the RustHDL widget library" as open work.
- **Spade.** Small but growing.

This is RHDL's biggest gap and, per the Tier-1 intervention point above, the obvious place to apply AI assistance.

### Toolchain & vendor support

- **Chisel.** First-class on most flows; well-trodden.
- **SpinalHDL.** First-class with most open and commercial flows.
- **RHDL.** `iverilog` integrated; `yosys`/`nextpnr`/Vivado not yet wired into `rhdl-toolchains` (which is just over 800 LOC at the moment).
- **Spade.** Open-source toolchain wiring.
