# `#[kernel]` constraints hit while implementing Modbus RTU slave (2026-04-29)

## Context

Attempted to implement `serial_bus::modbus_rtu_slave` as the
counterpart to the existing `modbus_rtu_master` widget.  The widget
needs to: receive UART bytes, accumulate a Modbus RTU frame
(addr | fc | data | crc-lo | crc-hi), validate CRC + address,
dispatch on function code, execute against an internal register
bank, build a response with its own CRC, and stream it out one byte
per `tx_ready` strobe.

Standard "fully fledged" coverage is ~10 function codes (0x01–0x06,
0x0F, 0x10, 0x11, 0x16, 0x17).  Even the slimmest useful subset —
register access only (FC 0x03, 0x04, 0x06, 0x10) — runs into RHDL's
current `#[kernel]` language constraints in three structural places.

The draft was scrapped rather than shipped as a half-broken v1.
This note documents the constraints so the next implementation
attempt (or RHDL-language-extensions PR) starts from the right
place.

## Constraint 1 — Helper kernels can't take array references

The CRC-16 over the response buffer is a per-byte iterative
computation:

```rust
fn compute_response_crc(buf: &[Bits<8>; N], len: Bits<8>) -> Bits<16> {
    let mut crc = bits::<16>(0xFFFF);
    for i in 0..N {
        if (i as u128) < len.raw() as u128 {
            crc = crc16_step(crc, buf[i]);
        }
    }
    crc
}
```

Compile error:
```
error: Unsupported expression type & d.resp_buf in an rhdl kernel function
```

The `#[kernel]` attribute rejects `&[T; N]` as an argument type
(the kernel-as-pure-fn invariant per `architecture.md` §1 forbids
references entirely — including immutable slice/array references).

**Workarounds, in order of preference:**

1. **Inline the helper into the main kernel.**  Each call site
   gets the per-byte loop unrolled in place.  Fine for one or
   two call sites; explodes the IR for the four call sites
   Modbus needs (one per FC arm).
2. **Multi-cycle CRC walker as a separate FSM state.**  Add a
   `ComputeRespCrc` state that walks the response buffer one
   byte per cycle, accumulating the CRC into a DFF.  Adds N
   cycles of latency per response (negligible for Modbus's
   ~ms timescales).  Cleanest for this widget.
3. **Take the buffer by value.**  `fn compute_resp_crc(buf:
   [Bits<8>; N], len: Bits<8>) -> Bits<16>`.  This works for
   small arrays but the call site has to copy the whole
   array each time, which makes the IR worse than #1.

**Language fix that would unblock #1:** allow immutable
`&[T; N]` (and `&T` for any `Digital` T) in helper kernel
arguments.  The kernel-as-pure-fn invariant is preserved
because the reference is passed *by value* — the function
can't mutate through it (no `&mut`), and there's no aliasing
concern in pure-functional code.  This would require minor
work in the `#[kernel]` macro AST translation; downstream
RHIF generation already handles aggregate slot reads.

## Constraint 2 — Arrays of size > 32 have no `Default` impl

```rust
struct ModbusRtuSlave<...> {
    req_buf: dff::DFF<[Bits<8>; 64]>,
    // ...
}
```

Compile error:
```
error[E0277]: the trait bound `[rhdl::prelude::Bits<8>; 64]: std::default::Default`
              is not satisfied
```

This is a **standard-Rust** limitation (not RHDL-specific): `impl
Default for [T; N]` is generated by the compiler only for `N` in
0..=32.  RHDL inherits this because `dff::DFF<T>` requires
`T: Default` to provide the post-reset value.

**Workarounds:**

1. **Limit array sizes to 32.**  Modbus standard frame max is 256
   bytes (FC 0x10 with 123 registers = 1+1+2+2+1+246+2 = 255), so
   32 isn't enough for the spec; it constrains the slave to
   shorter requests.  Returns ILLEGAL_DATA_VALUE for longer ones.
2. **Manually impl `Default` on a wrapper type:**

   ```rust
   #[derive(Clone, Copy, PartialEq, Debug, Digital)]
   pub struct Buf<const N: usize>([Bits<8>; N]);
   impl<const N: usize> Default for Buf<N>
   where rhdl::bits::W<N>: BitWidth, [Bits<8>; N]: Sized {
       fn default() -> Self { Self([bits::<8>(0); N]) }
   }
   ```

   But `[T; N]` initialisation with `[expr; N]` for non-`Copy`
   `Digital` types is its own can of worms.  And `Bits<8>` may
   or may not be `Copy` from RHDL's perspective for arbitrary N.
3. **Switch to a `dff::DFF<u8>` array** — i.e., `[dff::DFF<Bits<8>>;
   64]`.  This is N separate DFF sub-circuits, exposed in `Q` as
   N separate fields.  Bypasses the array-Default issue but blows
   up the kernel's `q.req_buf[i]` access pattern (you can't index
   into a tuple of DFFs at a runtime `i`).
4. **Manual array reset code in the kernel** — leave `dff::DFF`
   default-constructed with whatever it starts at, and clear the
   buffer via assignment in the reset arm.  Doesn't compile: same
   `Default` requirement on the field.

**Language fix that would unblock this:** RHDL provides a
blanket `Default` impl for `[T; N] where T: Default + Digital`
of any const-generic `N` (using `array::from_fn(|_| T::default())`
internally).  This is purely a library-side addition; no
language change needed.  Worth a small PR against `rhdl-bits`
or `rhdl-core`.

## Constraint 3 — Indexed reads / writes on DFF arrays inside a kernel

Even with Constraint 2 worked around, the kernel pattern:

```rust
d.req_buf[idx.raw() as usize] = i.rx_byte;
```

works for compile-time-constant indices but is fragile for
runtime indices: `idx.raw()` is the raw bits accessor, which works
in the simulator but may produce unexpected RHIF for the dynamic
indexing.  Modbus needs runtime indexing pervasively (bytes come
in one at a time at unpredictable counts).

**Workaround:** use `Index` semantics with `Bits<N>` indices
explicitly.  RHDL has `Path::dynamic_index(slot)` at the IR
level; the macro should expose this via `array[bits_idx]`
syntax.  In current RHDL, runtime array indexing inside a
`#[kernel]` is supported but the access-pattern interaction
with arrays-of-DFFs (where each "element" is its own SSA value)
is brittle.

This needs a real test case in `crates/rhdl/tests/` to pin
behaviour before building widgets that depend on it.

## Constraint 4 — Kernel-macro IR-size explosion (already documented)

The 4-arm dispatch on FC, with each arm building a multi-byte
response that includes a CRC-walk loop (per Constraint 1
workaround #1), produces a kernel that probably trips the same
IR-explosion that the MIDI parser hit (see
`notes/kernel-macro-oom.md`).  I didn't get to a clean compile
to confirm, but the structural pattern is the same: many
construction paths × non-trivial per-path logic = exponential
expansion.

## Recommended path forward for Modbus

The right shipping order is:

1. **Land the language / library fixes for Constraints 1, 2, and 3
   first.**  Each is a small, focused PR.  Together they convert
   "can't do Modbus cleanly" into "Modbus is straightforward."
2. **Then land Modbus slave**, taking advantage of the cleaner
   primitives.  Estimated ~800 LOC for the slave with full FC 0x03 /
   0x04 / 0x06 / 0x10 / 0x16 coverage; another ~700 LOC to extend
   the existing master to all FCs.
3. **Coil function codes (FC 0x01, 0x02, 0x05, 0x0F)** ship as a
   separate widget that shares the wire-layer + framing + CRC code
   with the register-access widget (factor a `modbus_rtu_framing`
   core out of both).

If you instead want Modbus slave to ship *now* without the language
fixes, the minimum viable version is FC 0x06 (Write Single Register)
only — no looping, no array-CRC, no large buffers.  ~250 LOC.
Useful for HOST-CONFIGURATION scenarios where the FPGA accepts
parameter writes from a host but doesn't do bulk register reads.
Documented as a sliver in the CHANGELOG, with the "fully fledged"
follow-up explicitly tracked.  Recommend NOT going this route per
the CLAUDE.md TL;DR rule (no v1 silently); land the language fixes
first.

## Related — also blocks CAN RX and SCSI

The same constraints will hit:

- **CAN 2.0A RX** — needs to accumulate frame data into a buffer
  (up to 8 data bytes + 15-bit CRC scratch), then walk it for CRC
  verification and ACK timing.  Same constraint-1 + constraint-3
  combination.
- **SCSI Parallel** — buffers SCSI command descriptor blocks
  (CDBs of 6, 10, 12, or 16 bytes) and data-phase blocks (up to
  256 bytes).  Constraint 2 (arrays > 32) directly applicable.
  Plus the FSM is large enough that constraint 4 (IR-size
  explosion) becomes likely.

Landing the four library / language fixes unblocks all three
widgets at once.
