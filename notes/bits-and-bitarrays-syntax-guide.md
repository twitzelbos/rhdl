# Bits & bitarrays — what works today

*Captured 2026-05-02. Audience: AI agents (and humans) writing `#[kernel]` bodies. The goal is to stop re-deriving the same shift-and-mask idioms that already have a cleaner form in the existing API.*

This is a working-knowledge guide. Everything described here is **already shipped** in `rhdl-bits` and `rhdl-macro-core`; nothing in this document depends on a future feature. For the surgical-fix follow-ups (`bits!()` macro, `slice::<HI, LO>()` method, `concat!()` macro, etc.) see `notes/rv32i-pain-to-surgical-compiler-fixes.md`.

---

## 1 — Constructing `Bits<N>` values

The canonical constructor is the function `bits::<N>(value: u128) -> Bits<N>` in `rhdl-bits/src/bits_impl.rs:98`:

```rust
let v: Bits<8>  = bits::<8>(0b1010_1010);
let m: Bits<32> = bits::<32>(0xFFFF_F000);
let z: Bits<5>  = bits::<5>(0);
```

There are 128 type aliases and constructor functions auto-generated by the `seq!` macro at `bits_impl.rs:74-83`. For every `N` in `1..=128`:

```rust
pub type b<N> = Bits<N>;
pub fn  b<N>(value: u128) -> b<N>;
```

So `b8`, `b16`, `b32`, etc. are types, and `b8(...)`, `b16(...)`, `b32(...)` are constructors. **Use these instead of `bits::<N>(...)` whenever the width is small and named.**

```rust
// Verbose:
let v: Bits<8>  = bits::<8>(0b1010_1010);
let m: Bits<32> = bits::<32>(0xFFFF_F000);

// Idiomatic:
let v: b8  = b8(0b1010_1010);
let m: b32 = b32(0xFFFF_F000);
```

Both forms emit identical Verilog. The `b<N>` form is preferred for readability.

There is also `bits_masked::<N>(value)` (line 119) which silently masks any high bits; useful when you've computed a value that may exceed `N` bits and want to truncate rather than panic. Used sparingly — `bits()` is preferred because it asserts at construction.

### Constants

Three associated constants are available on every `Bits<N>`:

```rust
Bits::<8>::ZERO   // all zeros
Bits::<8>::MAX    // all ones (== Bits::<8>::MASK)
Bits::<8>::MASK   // all ones
```

Use these instead of `bits::<8>(0)` and `bits::<8>(0xFF)` where they apply.

## 2 — Bit-width manipulation: `resize`

`Bits<N>::resize::<M>() -> Bits<M>` (line 171) truncates from the top if `M < N` and zero-extends if `M > N`.

```rust
let wide:   b32 = b32(0xDEAD_BEEF);
let narrow: b8  = wide.resize();        // 0xEF — bottom 8 bits
let huge:   b64 = wide.resize();        // 0x0000_0000_DEAD_BEEF — zero-extended
```

The target width `M` is inferred from the binding's declared type, so you rarely need to write `wide.resize::<8>()` explicitly — the binding `let narrow: b8 = wide.resize();` is enough.

### Field extraction (TODAY's idiom)

To extract bits `[HI:LO]` from `instr: b32`, the canonical idiom is **shift then resize**:

```rust
//                              hi=11, lo=7  → Bits<5>
let rd: b5 = (instr >> 7).resize();

//                              hi=14, lo=12 → Bits<3>
let funct3: b3 = (instr >> 12).resize();

//                              hi=31, lo=25 → Bits<7>
let funct7: b7 = (instr >> 25).resize();
```

**Do NOT write `((instr >> N) & bits::<32>(MASK)).resize()`** — the `&` mask is redundant because `.resize()` already truncates the upper bits to fit the target width.

The rv32i decoder still uses the redundant-mask form for historical reasons; new code should drop the mask.

The `slice::<HI, LO>()` method proposed in the surgical-fixes plan (task #78) is a thin ergonomic wrapper around this exact pattern with a named `HI` parameter; until it ships, use `(x >> LO).resize()`.

## 3 — Signed ↔ unsigned reinterpretation

`Bits<N>::as_signed() -> SignedBits<N>` (line 179) reinterprets an unsigned value as 2's-complement signed. `SignedBits<N>::as_unsigned() -> Bits<N>` is the inverse.

```rust
// Sign-extend an immediate via the signed-shift trick:
let raw: SignedBits<32> = instr.as_signed();
let sext: Bits<32>      = (raw >> 20).as_unsigned();
//                          ^^^^^^^^ arithmetic shift (sign-extending)
//                                    because raw is SignedBits
```

This is exactly what `decoder::imm_i` does — the trick is to convert to signed *first*, perform an arithmetic right shift (which sign-extends), then convert back. The Bits<N> right-shift is logical (zero-fills); the SignedBits<N> right-shift is arithmetic (sign-extends).

### Useful pattern: SRA

Same trick for arithmetic shift in the ALU:

```rust
AluOp::Sra => (a.as_signed() >> shamt).as_unsigned(),
```

This is what `alu.rs` does. Clean, idiomatic, no special compiler support needed.

## 4 — Operators

All standard Rust operators work on `Bits<N>` and `SignedBits<N>`:

| Operator class | Operators | Notes |
|---|---|---|
| Arithmetic | `+ - *` | Wrapping (2's-complement) per `rhdl-bits` semantics |
| Bitwise    | `& \| ^ !` | `!` is bitwise NOT of all `N` bits |
| Shift      | `<< >>` | `Bits<N> >>` is logical; `SignedBits<N> >>` is arithmetic |
| Compare    | `== != < <= > >=` | Unsigned for Bits<N>, signed for SignedBits<N> |

`!=` works directly:

```rust
if (instr >> 31).resize::<1>() != b1(0) {
    // sign bit is set
}
```

For division and remainder: the `b<N>` types do NOT implement `Div`/`Rem` directly (hardware integer divide is expensive and usually a separate widget). If you need division, use a widget from the library or compute it externally.

## 5 — Match expressions on `Bits<N>` — what works today

**Match on `Bits<N>` using the constructor-form literal pattern works.** `crates/rhdl/tests/literals.rs` has a working example:

```rust
#[kernel]
pub fn classify(x: b8) -> b3 {
    match x {
        Bits::<8>(0) => b3(0),
        Bits::<8>(1) => b3(1),
        Bits::<8>(2) => b3(1),
        Bits::<8>(3) => b3(2),
        _ => b3(4),
    }
}
```

The pattern `Bits::<N>(literal)` is a tuple-struct pattern that matches against the constructor. The rv32i decoder's funct3 dispatch could be (and should have been) written this way:

```rust
// IDIOMATIC: match on Bits<N> with constructor patterns
match funct3 {
    Bits::<3>(0b000) => if funct7 == b7(0b0100000) { AluOp::Sub } else { AluOp::Add },
    Bits::<3>(0b001) => AluOp::Sll,
    Bits::<3>(0b010) => AluOp::Slt,
    Bits::<3>(0b011) => AluOp::Sltu,
    Bits::<3>(0b100) => AluOp::Xor,
    Bits::<3>(0b101) => if funct7 == b7(0b0100000) { AluOp::Sra } else { AluOp::Srl },
    Bits::<3>(0b110) => AluOp::Or,
    Bits::<3>(0b111) => AluOp::And,
}
```

Match exhaustiveness still applies; if you cover all `2^N` values with explicit arms you can omit the `_` wildcard, otherwise add one.

**Or-patterns on Bits<N> match arms also work** (per task #30, shipped):

```rust
match priority {
    Bits::<2>(0) | Bits::<2>(1) => Tier::High,
    Bits::<2>(2)                => Tier::Mid,
    Bits::<2>(3)                => Tier::Low,
}
```

### What does NOT work today

- Bare integer literal patterns on `Bits<N>` scrutinees:
  ```rust
  match funct3 {
      0b000 => ...,   // ❌ doesn't compile — does not coerce
      0b001 => ...,
  }
  ```
  Use `Bits::<3>(0b000) => ...` until task #81 (kernel-language-extensions §2) lands.

- Range patterns:
  ```rust
  match opcode {
      Bits::<7>(0b0110011)..=Bits::<7>(0b0110111) => ...,   // ❌ not yet
  }
  ```

- Match guards: explicitly rejected by the kernel macro (see `match_ex` in `rhdl-macro-core/src/kernel.rs:1330`):
  ```rust
  match x {
      Bits::<8>(v) if v > Bits::<8>(10) => ...,  // ❌ — guard error
  }
  ```

## 6 — Useful methods

Beyond the constructors and `resize`/`as_signed`/`as_unsigned`/`raw`:

| Method | Purpose | Where |
|---|---|---|
| `.any() -> bool` | True iff any bit is set (== nonzero) | `bits_impl.rs:214` |
| `.all() -> bool` | True iff every bit is set (== `MASK`) | `bits_impl.rs:219` |
| `.len() -> usize` | Returns `N` (the bit width) | `bits_impl.rs:144` |
| `.is_empty() -> bool` | True iff `N == 0` | `bits_impl.rs:148` |
| `.dyn_bits() -> DynBits` | Convert to runtime-typed (kernel: rare) | `bits_impl.rs:193` |

Use `.any()` for "is any bit set" instead of `!= b<N>(0)` when readability matters:

```rust
// Verbose:
if (instr >> 31).resize::<1>() != b1(0) { /* sign bit set */ }

// Cleaner:
if (instr >> 31).resize::<1>().any() { /* sign bit set */ }
```

Both are equivalent at the IR level.

### Methods NOT yet present

- `count_ones()`, `count_zeros()`
- `leading_zeros()`, `trailing_zeros()`
- `rotate_left(n)`, `rotate_right(n)`
- `reverse_bits()`, `swap_bytes()`

These are on the kernel-language-extensions §3.1 list but not yet shipped. If you need any of them, write the loop yourself (per the `for i in 0..N` bounded-loop pattern) or factor into a helper widget.

## 7 — Common patterns

### 7.1 — Field extraction from a wide value

```rust
// Extract opcode (bits 6:0), funct3 (bits 14:12), funct7 (bits 31:25)
// from a 32-bit RV32I instruction.

let opcode: b7 = instr.resize();              // bits 6:0 — no shift needed
let funct3: b3 = (instr >> 12).resize();      // bits 14:12
let funct7: b7 = (instr >> 25).resize();      // bits 31:25
```

**Do NOT write the redundant-mask form** `((instr >> N) & b32(MASK)).resize()`. The mask is redundant once you `resize` to the target width.

### 7.2 — Building a wide value from bit fragments

For now, this is verbose because there's no `concat!()` macro. The standard idiom is shift-and-OR:

```rust
// Build imm_b: { sign_ext_19, instr[31], instr[7], instr[30:25], instr[11:8], 0 }
// (TODAY's idiom — verbose, but correct)

let bit12     = ((instr >> 31).resize::<1>().raw() << 12) as u128;
let bit11     = ((instr >>  7).resize::<1>().raw() << 11) as u128;
let bits_10_5 = ((instr >> 25).resize::<6>().raw() <<  5) as u128;
let bits_4_1  = ((instr >>  8).resize::<4>().raw() <<  1) as u128;
let combined: b32 = bits(bit12 | bit11 | bits_10_5 | bits_4_1);
let sign_mask: b32 =
    if (instr >> 31).resize::<1>().any() { b32(0xFFFF_E000) } else { b32(0) };
combined | sign_mask
```

The cleaner form will arrive when task #82 ships `concat!()` + `repeat!()`.

### 7.3 — Sign-extending an immediate

Use the signed-shift trick (per §3 above):

```rust
// I-type: immediate is bits [31:20], sign-extended to 32 bits.
fn imm_i(instr: b32) -> b32 {
    let raw: SignedBits<32> = instr.as_signed();
    (raw >> 20).as_unsigned()       // arithmetic shift sign-extends
}
```

This works only when the immediate's bits are contiguous and end at bit 31. For B-type and J-type immediates (where bits are scrambled), use the shift-and-OR form in §7.2.

### 7.4 — Setting a single bit

```rust
let with_bit_3 = original | b32(1 << 3);
```

Or via the builder pattern (less common):

```rust
let with_bit_3 = original | b32(0x08);
```

Use whichever is clearer at the call site.

### 7.5 — Conditional assign with default

The "compute a value with a fallback when a guard fails" pattern is important inside kernels because **both branches of an `if` always execute** (kernel `if` lowers to a combinational mux). If one branch would panic or trip a VM bound check, clamp the operand:

```rust
// WRONG — even when guard is false, the right-shift still runs at VM time:
let safe = if shamt < b8(8) { x >> shamt } else { b32(0) };

// RIGHT — clamp the operand so the right-shift always sees a valid value:
let safe_shamt = if shamt < b8(8) { shamt } else { b8(0) };
let safe = if shamt < b8(8) { x >> safe_shamt } else { b32(0) };
```

See the barrel-shifter widget for a worked example. The same principle applies to any operation with VM-enforced bounds (right-shift by `>= N`, array index out-of-range, etc.).

## 8 — Common mistakes to avoid

**1. Writing `((x >> N) & b32(MASK)).resize()` instead of `(x >> N).resize()`.** The mask is redundant; resize truncates from the top.

**2. Using `bits::<32>(0)` everywhere instead of `b32(0)` or `b32::ZERO`.** The `b<N>` aliases are shorter and cleaner.

**3. Using bare integer match arms on `Bits<N>` scrutinees** (`match x { 0 => ..., 1 => ... }`). Use the constructor form `Bits::<N>(0)` or pre-declare named constants.

**4. Trying to use match guards.** Rejected by the kernel macro. Pre-compute the guard's result into a `let` binding and use it in the body, or split into separate match arms.

**5. Trying to write a kernel with references** (`&T`, `&mut T`). Pass by value. RHDL kernels are pure functions over `Digital` values; references don't exist in hardware. Per CLAUDE.md §6, `Digital` types are all `Copy`, so passing by value has no overhead.

**6. Mixing `Bits<N>` and `SignedBits<N>` arithmetic.** Always convert explicitly via `.as_signed()` / `.as_unsigned()`. The two types are deliberately distinct so that signed-vs-unsigned bugs surface at compile time.

**7. Trying to perform arbitrary-width arithmetic.** `Bits<N>` is capped at `N <= 128`. For wider data, compose via tuples, structs, or arrays — but you cannot do `add` on a `Bits<256>`.

## 9 — Stable vs. nightly Rust — what's possible to express

RHDL targets stable Rust. Several "obviously cleaner" type signatures for proposed extensions actually require **`feature(generic_const_exprs)`**, which is nightly-only and not on a stabilization path. The replacement effort, **`min_generic_const_args` (MGCA)**, is in prototype phase as of mid-2025 with no committed stabilization timeline as of May 2026 — and may be blocked on the new trait solver landing first. Treat anything that requires either feature as "not realistic for the next 12-24 months."

### What requires nightly

A method like `slice<const HI: usize, const LO: usize>(self) -> Bits<{HI - LO + 1}>` requires `generic_const_exprs` because it computes the result type via const arithmetic in a generic position. The same applies to any signature where one type parameter is a function of others.

### Stable workaround patterns

- **Pass the result width as a separate const param.** `slice::<W, LO>() -> Bits<W>`; caller computes `W = HI - LO + 1` themselves. Verbose at the call site but fully stable.
- **Use a proc-macro instead of a method.** `slice!(instr, 11, 7)` expands to `(instr >> 7).resize::<5>()` — the macro computes the width at expansion time, no `generic_const_exprs` needed. Clean call-site syntax, fully stable Rust.

The `slice!()` proc-macro form is the path the surgical-fix plan now takes for Task #78.

### The kernel macro can rewrite some things rustc would reject

Some proposed extensions (like bare-integer match arms on `Bits<N>` scrutinees — `match funct3 { 0b000 => ... }`) produce Rust that **rustc itself would reject** with "mismatched types: expected `Bits<3>`, found integer." The kernel `#[kernel]` proc-macro receives the function's TokenStream **before rustc type-checks it**, so it can rewrite `0b000 => ...` to `Bits::<3>(0b000) => ...` before emitting. The rewritten form passes rustc.

This means: such syntax is **kernel-only**. It works inside `#[kernel] fn foo(...)` but not in regular Rust functions. Other agent-visible kernel-only extensions (or-patterns inside non-enum patterns, certain bounded loops, etc.) follow the same model.

When you see "Task #N proposes `match funct3 { 0b000 => ... }` syntax," remember:
- Outside `#[kernel]`: rejected by rustc (type mismatch).
- Inside `#[kernel]`: rewritten by the macro before rustc sees it, then passes type-check.

### Summary table

| Proposed form | Stable Rust? | How it ships |
|---|---|---|
| `bits!(0x1F)` macro | ✅ yes | Proc-macro expansion |
| `slice!(instr, 11, 7)` macro | ✅ yes | Proc-macro expansion |
| `instr.slice::<11, 7>() -> Bits<{HI - LO + 1}>` method | ❌ needs `generic_const_exprs` | Nightly-only; or use the macro form |
| `instr.slice::<W, LO>() -> Bits<W>` method (W explicit) | ✅ yes | Stable; verbose call site |
| `match x { Bits::<3>(0b001) => ... }` | ✅ yes | Already shipped (literals.rs) |
| `match x { 0b001 => ... }` (bare on `Bits<N>`) | ❌ rustc rejects directly | Kernel-only via macro AST rewrite |
| `concat!(...)`, `repeat!(...)` macros | ✅ yes | Proc-macro expansion |
| `Bits<{N+M}>` arithmetic in arbitrary type positions | ❌ needs `generic_const_exprs` | Wait for MGCA stabilization, or work around with macros |

**Heuristic — first cut:** if a proposed extension needs to compute a type from arithmetic on const params, ship it as a proc-macro. If it needs to rewrite Rust syntax that rustc would reject, ship it as a kernel-macro AST rewrite.

### The Rust-purity criterion (preferred)

Both proc-macros and kernel-macro AST rewrites are technically "stable Rust" in that the final compiled output type-checks. But there's a stronger criterion worth applying: **does the syntax the user types pass the Rust-purity test from a coder's perspective?**

A proc-macro invocation (`bits!(...)`, `slice!(...)`, `concat!(...)`) is pure-Rust by this criterion: macros are a documented Rust mechanism, the user knows they're calling a macro, IDEs handle them, and the syntax inside is the macro's own DSL.

A kernel-macro AST rewrite that makes rustc-illegal syntax legal (e.g., `match bits_val { 0b001 => ... }` which rustc rejects with "mismatched types") is *not* pure-Rust by this criterion. From a coder's perspective, they wrote ordinary Rust syntax — but it only compiles inside the magic context. Copy the line outside the macro and rustc rejects it. That's surprising.

**Rule for new RHDL features:** prefer pure-Rust forms (proc-macros, methods, trait-based dispatch) over kernel-macro AST rewrites that make rustc-illegal syntax appear legal. The shipped rhdl-rule API does use AST rewriting (`RuleCtx<W>` is a phantom struct with only `PhantomData`, so `ctx.count` is invalid plain Rust — the macro rewrites it). That's a legacy decision the rule-architecture inherited; new proposals should not extend it.

**Concrete consequence for the rv32i pain points:** Task #81 (bare-integer match arms on `Bits<N>`) was originally proposed as a kernel-macro AST rewrite. Per the purity rule, that proposal is **dropped**. Use the already-working constructor form `Bits::<3>(0b001) => ...` from §5 — pure Rust, shipped, no compiler change needed. The rv32i decoder should be refactored to use this form; that's the canonical answer.

## 11 — TL;DR cheat-sheet for kernel authors

```rust
// Construct
let x: b8  = b8(0b1010_1010);             // not bits::<8>(0b1010_1010)
let z: b32 = b32::ZERO;                   // not b32(0)
let m: b32 = b32::MASK;                   // not b32(0xFFFF_FFFF)

// Field extract (no redundant mask)
let funct3: b3 = (instr >> 12).resize();  // bits [14:12]

// Signed
let sext: b32 = (instr.as_signed() >> 20).as_unsigned();

// Match (constructor-form literal patterns)
match funct3 {
    Bits::<3>(0b000) => /* ... */,
    Bits::<3>(0b001) => /* ... */,
    _ => /* ... */,
}

// Operators
let a_plus_b: b32 = a + b;       // wrapping
let bitwise:  b32 = a ^ b;
let shifted:  b32 = x >> shamt;  // logical
let signed_s: b32 = (x.as_signed() >> shamt).as_unsigned();  // arithmetic

// Methods
let any_bit_set: bool = x.any();
let all_bits_set: bool = x.all();
let width: usize = x.len();        // returns N
```

This cheat-sheet is the working subset every kernel author should already know. If you find yourself typing `(x >> N) & bits::<32>(MASK)` or `bits::<8>(0)`, re-read §1-§3.
