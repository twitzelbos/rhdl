# Compile, Don't Wait

## Why a Rust-Based HDL is the Right Substrate for LLM-Assisted Hardware Design

The hardware industry is on the cusp of an LLM-assisted productivity revolution that almost every other engineering discipline has already booked. Software engineers iterate on code with AI pairing partners that read compiler diagnostics, run unit tests, and steer toward correctness in minutes. Hardware engineers, by and large, do not. The reason is not that hardware is harder. The reason is that the conventional hardware development substrate — Verilog and SystemVerilog plus their elaborate simulator-and-vendor-tool ecosystem — was designed in an era when iteration cost was measured in coffee breaks. That substrate is fundamentally hostile to the way LLMs work best. A Rust-based HDL like RHDL changes the substrate, and that change is decisive.

This essay makes one claim, defended two ways. The claim is that Rust as a hardware description language is not merely a stylistic preference, not merely modern syntax, not merely a way to feel fashionable while writing gateware — it is the substrate that makes high-velocity LLM-assisted hardware design possible at all. The two defenses are compile-time correctness and the speed of validation. Together they form a feedback loop whose cycle time and signal quality are what determine whether an LLM is a useful collaborator or a frustrated hallucinator.

## The Iteration Cost Argument

Every effective LLM-assisted workflow is a hill-climbing search. The model proposes a candidate solution. Some oracle — a compiler, a test runner, a linter, a human review — emits a signal about whether the candidate is correct, and if not, why not. The model uses that signal to propose a better candidate. The loop runs until the signal says "done."

Two parameters dominate the productivity of this loop: the cycle time of one iteration, and the precision of the error signal at the end of each cycle. Cut cycle time in half and you can search twice as wide. Make the error signal more precise and the search converges in fewer iterations. Multiply the two effects and you compound. Conversely, a slow iteration loop with vague errors makes LLM assistance feel like talking to someone through a long-distance phone call with a three-second lag — possible, occasionally useful, never a partnership.

Traditional Verilog development has a brutally long iteration loop. The smallest meaningful round trip — edit a module, elaborate the design, run a simulator, observe a waveform, infer the bug — is rarely shorter than a minute and is often much longer. Many of the most common bugs in Verilog (driving the same wire from two `always` blocks, mismatched bit widths silently truncated, wrong sensitivity list, forgotten reset) produce no error at all at compile time; they produce wrong waveforms at simulation time, and only if the testbench happens to exercise the relevant condition. The error signal at the end of the loop is "the waveform looks weird." A human can sometimes diagnose that. An LLM, working from text, generally cannot.

This is the trap. The substrate makes the loop slow and the error signal weak. No amount of LLM cleverness can fix the substrate. The fix has to be in the substrate itself.

## What Rust Catches Before Anything Runs

A Rust-based HDL like RHDL catches an enormous class of hardware bugs at compile time, before any simulator is invoked. This is not "lint-style" catching, where you get a warning and the code still compiles. This is type-system-enforced refusal-to-build. The bug literally cannot exist in a binary that compiles. For an LLM-driven workflow, this is gold: every invocation of `cargo check` is an oracle that returns either "your candidate has these specific problems at these specific source locations" or "we proceed."

The first and most consequential category is *clock domain safety*. RHDL represents every signal as `Signal<T, Domain>`, where `Domain` is a phantom type parameter — a zero-sized marker, often colored (Red, Orange, Yellow, Green, Blue, Indigo, Violet). Two signals from different clock domains have *different Rust types*, and the compiler refuses to combine them with arithmetic, equality, or assignment. Crossing a clock domain requires an explicit `Retime` operation, which is the only place a multi-flop synchronizer can be introduced. In conventional Verilog, clock-domain crossings are detectable only by specialized CDC analysis tools after the fact, and most CDC bugs ship to silicon. In RHDL, a CDC bug is a Rust compile error pointing at the offending line. An LLM that emits an unsafe crossing gets the diagnostic in milliseconds and corrects it on the next attempt.

The second category is *algebraic data types making invalid states unrepresentable*. Hardware protocols are full of tagged unions: a packet is either a header, a payload chunk, or an end-of-frame; a bus transaction is either a read, a write, or an idle; an opcode carries operands whose count and shape depend on which opcode it is. In Verilog you encode these as bit fields with a discriminant and pray that nothing reads the payload bits when the discriminant says they're meaningless. In RHDL you encode them as Rust enums with payloads — the compiler guarantees that you can only access the payload via a `match` arm that has already established which variant you have. The hardware-mapping is automatic: discriminants get packed bits, payloads get layout-aligned. An LLM that tries to read `MyEnum::B(x, y).x` from a value known to be `MyEnum::A` does not produce wrong silicon; it produces a Rust compile error on a line.

The third category is *bit widths as types*. `Bits<8>` and `Bits<16>` are different types in RHDL. Adding them without explicit widening is a compile error. Casting them silently lies neither to you nor to the synthesizer. Const generics let widths flow through generic code, so `counter<N>` for any `N` is one piece of code with full type checking, not a textual macro that bursts into a thousand undebuggable variants. Width mismatches — the leading cause of "everything elaborates fine but produces garbage" bugs in Verilog — are a compile-time refusal in RHDL.

The fourth category is *flow correctness*. RHDL's compiler runs a battery of analyses on the intermediate representation between Rust and Verilog: a partial-initialization check (you cannot read a field you haven't written), a dataflow check (use-before-write is forbidden), a type-coverage check on `match` arms, a "single-driver" check on every register, a check for undriven nets, a check for zero-width outputs from synchronous blocks. In conventional Verilog these conditions are either runtime symptoms or warnings hidden inside thousand-line elaboration logs. In RHDL they are errors that the compiler refuses to produce a binary past.

The fifth category, sometimes underappreciated, is *structural correspondence between parents and children*. A RHDL synchronous circuit declares its sub-circuits as struct fields. The framework then derives a `D` type (inputs to all children) and a `Q` type (outputs from all children) automatically, and the kernel function's signature is `fn kernel(cr, i, q) -> (o, d)`. If you wire `q.child_1` into something that expects `child_2`'s output type, the compiler stops you. If a child you added in the struct never gets wired up in the kernel, the compiler stops you. This makes hierarchical composition — usually one of the most error-prone parts of large designs — a transaction the type system mediates.

The cumulative effect is that the *first* signal an LLM gets when it emits an RHDL kernel is overwhelmingly informative. Either the candidate is structurally and semantically sound at the type level, or the diagnostics name the line, the variable, the violated invariant, and (because RHDL routes errors through `miette`) suggest a fix. There is no equivalent in the Verilog ecosystem. The closest thing — a SystemVerilog elaboration error — typically arrives forty seconds later, in a vendor-tool log, with a message like `error: cannot resolve hierarchical reference`.

## What Validation Looks Like After the Type-Check Passes

Compile-time correctness eliminates an enormous class of bugs without running anything. The remaining bugs are algorithmic: the design type-checks, but it computes the wrong answer. For these, you need fast, high-fidelity simulation. The conventional flow involves writing a SystemVerilog testbench, invoking a commercial or open-source Verilog simulator, waiting for elaboration and compilation, running the simulation, dumping waveforms, opening a viewer. Even the fast paths take tens of seconds; the slow paths take hours. None of this fits inside an LLM iteration loop.

RHDL's answer is that *the kernel is just a Rust function*. This is the under-appreciated structural decision that changes everything downstream. A kernel is a normal `fn` over normal Rust types. You can call it from a Rust unit test the way you would call any other function. The widget library does this constantly: the `write_logic` kernel inside the synchronous FIFO has six unit tests in the same file that construct an input and a state by hand, call the kernel, and assert on the output. They run in milliseconds under `cargo test`. They run in parallel. They print Rust panic messages with file and line numbers when they fail. There is no simulator. There is no testbench language. There is no waveform viewer in the loop. There is only `cargo test`.

This first tier of validation — calling the kernel directly — handles the majority of algorithmic bugs in microseconds per test case. For the bugs it doesn't handle (sequencing, multi-cycle behavior, reset propagation), RHDL provides a second tier: an iterator-based simulator that runs the synchronous circuit cycle by cycle in pure Rust. Inputs are iterators. Outputs are iterators. The simulator is `uut.run(stream).collect::<Vec<_>>()`. There is no event loop in C++, no value-change-dump file, no linker, no foreign function interface. The simulator runs at native Rust speed and is itself unit-testable. The third tier validates the lowered netlist — the simulator that operates on RHDL's NTL intermediate representation, which catches bugs introduced by the lowering passes themselves. The fourth tier round-trips the emitted Verilog through `iverilog` or another standard simulator and diffs the waveforms against the Rust-side simulator output. Each tier is a `cargo test` invocation; each tier catches a different class of bug; each tier is fast enough to run in a feedback loop.

The numbers matter. A typical RHDL widget unit test runs in single-digit milliseconds. The full iterator-based simulation of a thousand-cycle FIFO trace runs in tens of milliseconds. The NTL flow-graph simulation runs slightly slower but in the same ballpark. The Verilog round trip is the slow one — seconds — and is reserved for final validation, not the inner loop. Compare this to a Verilog flow where opening the simulator alone can take ten seconds before any actual cycles are simulated. The asymmetry is enormous. A 100x speed-up in iteration cycle is not a quantitative improvement; it changes what kinds of search are feasible.

## Why This Compounds for LLMs Specifically

A human engineer benefits from these properties too, but a human can absorb a slow loop with patience and intuition. An LLM cannot. An LLM works by sampling candidates from a distribution conditioned on context. It does not have intuition; it has feedback. The faster and more precise that feedback, the better the candidates it can produce, because each error signal is a piece of conditioning data for the next attempt.

In the RHDL setting, an LLM's iteration loop looks like this. It proposes a kernel. It runs `cargo check`. If the type system rejects, the diagnostics — line, column, expected type, actual type, often a structured suggestion — are fed back as context, and the LLM produces a corrected version. This typically converges in two or three rounds. Once the type check passes, the LLM runs `cargo test` against the unit tests, which take milliseconds. Failing tests give it specific input-output mismatches: "for input X the kernel returned Y but expected Z." The LLM produces a corrected version. Again, this typically converges in a small number of rounds. The whole process — from natural-language spec to passing-tests-on-a-real-FPGA-bound design — can complete in seconds of wall time, not minutes.

The contrast with the conventional flow is brutal. An LLM emitting Verilog gets feedback that is qualitatively worse at every step. The compiler accepts code that has critical bugs. The simulator runs slowly enough that running it inside the loop is impractical. The simulator's failure mode is a waveform, not a textual error — the LLM can't see waveforms efficiently, and even when it can, the diagnostic is "this signal is wrong at cycle 47" rather than "you forgot to assign `state` in the `default` case of your `case` statement." Each iteration is longer and produces less information. The hill-climb stalls.

The substrate determines the ceiling. With Verilog, the ceiling on LLM-assisted hardware productivity is low — not because the LLM is weak but because the feedback signal is. With RHDL, the ceiling is essentially the same as the ceiling on LLM-assisted software development in Rust, which is already very high.

## The Strategic Reading

A second-order consequence follows. Whichever ecosystem first reaches the point where LLMs can credibly co-author production hardware is going to absorb a disproportionate share of the next decade's design talent and vendor investment. The market doesn't care which HDL is most elegant on paper; it cares which one lets a small team ship a chip in three months instead of nine. The HDL that wins this race is the one with the tightest LLM-friendly feedback loop, and that loop is determined by the substrate's compile-time strictness and validation speed.

Verilog and SystemVerilog have entrenched ecosystem advantages — vendor tools, libraries, training data, deployed silicon. They also have a substrate that does not bend to LLMs. Chisel and SpinalHDL are newer and stronger but live inside Scala, with a runtime-graph-construction model that does not present a clean compile-time correctness boundary. Spade is interesting but small. RHDL — Rust as a hardware description language, with a real multi-stage compiler, phantom-typed clock domains, ADT-aware synthesis, and the entire `cargo test` ecosystem as its testbench — is the substrate that is shaped exactly the way an LLM wants the world to be shaped.

That is the manifesto. Compile-time correctness eliminates whole classes of bug before any cycle is simulated. Speed of validation makes iteration cheap enough to search widely. The combination produces a feedback loop whose properties are decisive for LLM-assisted development. Hardware design has been waiting for its productivity inflection point. The substrate is here. The implication is straightforward: build the tools and libraries on this substrate now, while it is still emerging, and dominate the design flow that the rest of the industry will be reaching for in eighteen months.

Compile, don't wait.
